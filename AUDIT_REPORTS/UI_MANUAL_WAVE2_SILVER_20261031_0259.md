## ۵) یافته‌ها

### SIL-01 — ناسازگاری schema با مدل‌های ORM (Critical)

**شواهد:**
- `GET /api/v1/brsapi/commodities?category=precious_metal&latest_only=true` → HTTP 200، `success:false`، `error.message:"Internal error"`. لاگ سرور: `UndefinedColumnError: column brsapi_commodity_prices.ins_id does not exist`.
- `GET /api/v1/brsapi/currency` و `/brsapi/gold-coin` و `/brsapi/crypto` → همان `success:false / Internal error` (شاهد: `audit_out/ui_test_backend_silver.log`).
- `GET /api/v1/gold/ime/futures` → `UndefinedColumnError: column brsapi_ime_futures.bid_volume_1 does not exist` (همان لاگ؛ متن SQL کامل در پاسخ API).
- `GET /api/v1/funds/{symbol}/nav-split` → `UndefinedColumnError: column brsapi_nav_records.ins_id does not exist`.
- DDL پایه: `migrations/versions/0004b_core_baseline.py:385-429` جدول `brsapi_ime_futures` را بدون `bid_volume_1..3` / `bid_price_1..3` / `ask_volume_1..3` / `ask_price_1..3` می‌سازد؛ `:611-620` جدول `brsapi_nav_records` را بدون `ins_id`/`instrument_id` می‌سازد.
- مدل‌ها: `brsapi/models/base.py:21-35` (`InstrumentRefMixin` با `ins_id` و `instrument_id`) و `brsapi/models/ime.py:65` (`bid_volume_1` و …).
- شمارش: ۲۷ کلاس مدل از `InstrumentRefMixin` استفاده می‌کنند؛ در DB تست فقط ۴ جدول از این خانواده ستون `ins_id` دارند (`brsapi_ime_funds`, `brsapi_option_snapshots`, `brsapi_symbol_snapshots`, `brsapi_symbol_details`).

**بازتولید:** با دیتابیس ساخته‌شده از `alembic upgrade head` (اینجا 0120) هر یک از endpointهای بالا را صدا بزنید؛ حتی با صفر ردیف داده، خطای ستون غایب رخ می‌دهد.

**اثر:** صفحهٔ نقره نمی‌تواند قیمت انس/دلار/آتی/NAV را نشان دهد؛ همین نقص صفحات طلا، کریپتو، gold-fx، هیتمپ و … را هم درگیر می‌کند (خطاهای `Internal error` در همان لاگ).

**اصلاح پیشنهادی (نیازمند تأیید، اجرا نشده):** یک مایگریشن جدید (مثلاً 0121) که با `ALTER TABLE … ADD COLUMN IF NOT EXISTS` ستون‌های غایب را برای همهٔ جدول‌های `InstrumentRefMixin` و ستون‌های سفارش‌بوک `brsapi_ime_futures` اضافه کند؛ سپس تست: هر ۵ endpoint باید `success:true` بدهند و `alembic heads` تنها یک head داشته باشد. **هیچ migrationای در این موج اجرا نشد.**

### SIL-02 — بلعیدن خطای DB در `nav-split` و نمایش «یافت نشد» (High)

**شواهد:** `apps/api/endpoints/funds.py:1544-1556` —
```python
try:
    ... select(NavRecordModel) ...
except Exception as exc:
    logger.debug("NAV split unavailable for %s: %s", symbol, exc)
    row = None
if row is None:
    return {"symbol": symbol, "found": False, "latest": None}
```
لاگ: `NAV split unavailable for سیلور: … column brsapi_nav_records.ins_id does not exist`، اما پاسخ HTTP 200 با `found:false` بود.

**اثر:** در UI، حباب NAV و ستون‌های NAV صدور/ابطال به‌جای خطا «—» یا «موجود نیست» نشان می‌دهند؛ کاربر و اپراتور نمی‌فهمند داده هست ولی خواندنش شکست خورده. این مستقیماً قاعدهٔ «خطا را از خالی تفکیک کن» را نقض می‌کند.

**اصلاح پیشنهادی:** فقط `NoResultFound`/نبود ردیف را `found:false` کنید؛ خطاهای DB را بالا بدهید (یا پاسخ `503` با کد خطای مشخص). UI هم باید حالت خطای NAV را جدا نشان دهد.

### SIL-04 — اشباع اتصال و تأخیر hydration در بار اول (Medium؛ محیط‌تقویت‌شده)

**شواهد:** در دو اجرای اول، ۱۵ و ۲۵ ثانیه بعد از بارگذاری، هیچ React prop روی دکمه‌های تب نبود و همهٔ chunkهای `_next/static/chunks/*` در حالت pending بودند (۱۸+ ثانیه). curl همان chunk را در ۱۰ms می‌دهد. پس از پایان درخواست‌های کند، hydration در ۳۶ ثانیه انجام شد. درخواست‌های در جریان شامل ۱۱ endpoint سراسری shell (`enriched-heatmap`, `news`, `gold-coin`, `currency`, `crypto`, `indices`, `treemap`, `market-dashboard`, `flow-summary`, `flow-history`, `economic-calendar`) و سپس ۶+ درخواست خود صفحهٔ نقره بود.

**اثر:** در شبکه/بک‌اند کند، کاربر صفحه‌ای می‌بیند که دکمه‌هایش تا ده‌ها ثانیه بی‌اثرند. در production با HTTP/2 این محدودیت ۶ اتصال وجود ندارد، اما تعداد بالای فراخوانی‌های اولیه و retry/timeoutهای ۶۰ ثانیه‌ای همچنان ریسک است.

**پیشنهاد:** کاهش فراخوانی‌های اولیهٔ shell، استفاده از HTTP/2 در لبه، `staleTime`/`placeholderData` مناسب، و نمایش skeleton مستقل برای chunk/hydration. این مورد در تست به‌عنوان «محیط» علامت‌گذاری شد، نه باگ قطعی محصول.

**اصلاح پیشنهادی:** پس از خطای anchor، حالت خطای صریح با دکمهٔ «تلاش دوباره» نشان دهید و skeleton را به یک بازهٔ کوتاه محدود کنید.

## ۹) اقدامات بعدی به ترتیب اولویت

1. **SIL-01 (فوری):** افزودن مایگریشن برای ستون‌های `ins_id`/`instrument_id` و ستون‌های سفارش‌بوک `brsapi_ime_futures`؛ سپس تست دوبارهٔ ۵ endpoint و اجرای مجموعهٔ تست‌های migration. نیازمند تأیید صریح شما (تغییر schema).
2. **SIL-02 (فوری):** حذف `except Exception` بلعنده در `funds.py` و تفکیک «یافت نشد» از «خطای DB»؛ افزودن حالت خطای NAV در UI.
3. **SIL-03 (کوتاه‌مدت):** یکسان‌سازی envelope خطا با `error_code`/`trace_id`؛ حذف SQL از پاسخ کلاینت.
4. **SIL-05 (کوتاه‌مدت):** اعتبارسنجی ورودی مبدل (`—` برای ورودی نامعتبر/منفی) + تست واحد برای فرمول و حالت‌های مرزی.
5. **SIL-06 (کوتاه‌مدت):** نمایش خطای صریح + retry در تب پیش‌بینی وقتی anchor در دسترس نیست.
6. **SIL-04 (میان‌مدت):** کاهش فراخوانی‌های اولیهٔ shell و بررسی HTTP/2/edge؛ اندازه‌گیری TTI با Lighthouse در محیط آزمایشی.
7. **داده:** برای تست کامل صندوق/NAV/خبر/آتی، یک دیتاست ساختگیِ قابل‌شناسایی (fixture) در DB آزمایشی بارگذاری شود؛ سپس موج تست دوباره اجرا شود.
