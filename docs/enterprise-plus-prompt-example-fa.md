## ۶. Empty States و First-Time User Experience
- Given کاربر برای اولین بار وارد صفحه صندوق‌ها می‌شود و هیچ صندوقی در واچ‌لیستش نیست، When صفحه بارگذاری می‌شود، Then به‌جای صفحه خالی، پیشنهاد چند صندوق پرطرفدار یا راهنمای کوتاه «چطور شروع کنم» نمایش داده شود.

## ۷. حالت آفلاین/اتصال ضعیف
- Given اتصال اینترنت کاربر قطع یا بسیار کند است، When درخواست داده ناموفق می‌شود، Then آخرین داده کش‌شده (در صورت وجود) با برچسب واضح «داده ممکن است قدیمی باشد» نمایش داده شود، نه صفحه سفید یا خطای خام.

## نسخه‌بندی و سازگاری با گذشته (Versioning & Backward Compatibility)
- اگر مدل داده Fund در جای دیگری از پروژه (مثلاً بخش صندوق‌ها در صفحه اصلی یا ویجت خلاصه) استفاده می‌شود، تغییر ساختار داده نباید آن نقاط را بشکند؛ در صورت نیاز به تغییر breaking، یک لایه adapter/mapper بنویس تا مصرف‌کنندگان قدیمی داده هم‌چنان کار کنند.
- اگر API نسخه‌بندی دارد (v1/v2)، مشخص کن از کدام نسخه استفاده می‌شود و رفتار در صورت deprecated شدن نسخه فعلی چیست.

## استراتژی Rollout و Feature Flag
- در صورت وجود سیستم feature flag در پروژه، این ماژول ارتقایافته را پشت یک flag قرار بده تا امکان rollout تدریجی (مثلاً ابتدا ۱۰٪ کاربران) وجود داشته باشد.
- اگر feature flag وجود ندارد، حداقل کد را طوری ساختاردهی کن که نسخه قدیم و جدید بتوانند به‌صورت موازی (side-by-side) تا زمان اطمینان از پایداری وجود داشته باشند، نه جایگزینی یک‌باره و غیرقابل‌بازگشت.

## طرح بازگشت (Rollback Plan)
- در گزارش نهایی، مشخص کن در صورت بروز مشکل جدی در production، چگونه می‌توان این تغییرات را سریع rollback کرد (بازگشت به کامیت قبلی، غیرفعال کردن flag، یا حذف فایل‌های مشخص).

## طبقه‌بندی خطا (Error Taxonomy)
خطاهای این ماژول را به دسته‌های زیر تقسیم و برای هرکدام پیام و رفتار UI مشخص کن (نه یک پیام خطای عمومی برای همه):
1. خطای شبکه (عدم دسترسی به API) → پیام «اتصال برقرار نیست» + دکمه تلاش مجدد
2. خطای داده ناقص/نامعتبر از API → لاگ خطا برای توسعه‌دهنده + نمایش صندوق‌های معتبر و نادیده گرفتن رکورد خراب (نه کرش کل صفحه)
3. خطای عدم وجود داده کافی برای محاسبه (مثل شارپ) → نمایش «—» با توضیح، نه خطا
4. خطای Rate Limit از سمت API → پیام موقت و retry با backoff، نه درخواست مکرر فوری

## چک‌لیست ریویو کد (Code Review Checklist)
قبل از اعلام اتمام کار، خودت این چک‌لیست را روی کدت اجرا کن:
- [ ] آیا نام‌گذاری متغیرها/توابع گویا و سازگار با conventions موجود پروژه است؟
- [ ] آیا هیچ کد کپی‌شده تکراری (duplicate) بین این ماژول و ماژول‌های مشابه دیگر (مثلاً بازار کالا) وجود دارد که می‌شد share شود؟
- [ ] آیا هیچ console.log یا کد دیباگ در نسخه نهایی باقی نمانده؟
- [ ] آیا مدیریت حافظه رعایت شده (cleanup subscriptions/intervals در useEffect یا معادل، برای جلوگیری از memory leak در صفحه‌ای که کاربر مدت طولانی باز نگه می‌دارد)؟
- [ ] آیا تمام رشته‌های قابل نمایش به کاربر (نه کد) از یک منبع متمرکز متن (در صورت وجود سیستم i18n) می‌آیند، نه hardcode پراکنده؟

# استراتژی تست (تکمیل‌شده)
(unit/integration/edge case از قبل) +
- **Visual Regression (در صورت وجود ابزار مربوطه در پروژه، مثل Chromatic/Storybook)**: بررسی عدم تغییر ناخواسته ظاهری در کامپوننت‌های مشترک.

# مستندسازی و Handoff
- یک بخش کوتاه README یا کامنت سطح بالا در کد اضافه کن که توضیح دهد: این ماژول چه می‌کند، فرضیات مالی مهم (مثلاً نحوه محاسبه نسبت شارپ: annualized یا نه)، و نحوه افزودن یک نوع صندوق جدید در آینده توسط توسعه‌دهنده دیگر بدون نیاز به خواندن کل کد.
- هرگونه فرض غیرواضح مالی (مثلاً نرخ بدون ریسک استفاده‌شده در فرمول شارپ) باید صریح مستند شود، چون در صورت اشتباه مستقیم روی اعتماد کاربر به داده‌های مالی تأثیر می‌گذارد.
