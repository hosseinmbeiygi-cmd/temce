# Why TEMCE Is Not Reliably Finding Good Signals: Deeper Code Diagnosis

**Reviewed:** September 24, 2026 · **Repository revision:** `bc9fd2070a4003bbe4de8c888cd676563aa01046` · **Scope:** current checkout, not a running production instance. No repository files were changed. Findings below distinguish reproduced behavior, code-level risks, and historical observations.

## Bottom line

The problem is not merely that the trading rules need tuning. On the principal dashboard path, automatic retraining cannot reach its training threshold under normal data flow; outcomes are labelled on a fixed calendar schedule unrelated to the predicted horizon; and the reported per-market accuracy can be the accuracy of just one source rather than the whole market. These defects undermine the learn–measure–improve loop. The current checkout also cannot start its API because of committed conflict markers, so this review cannot verify the app against live prices or establish its *current* win rate.

## End-to-end trace

`frontend/src/app/signals/page.tsx:29-43` → `apps/api/endpoints/multi_market_signals.py:180-215` → `services/quant_signal_orchestrator.py:631-849` → `services/multi_market_signal_engine.py:357-410` (seven rule-based market generators) → ML history/prediction → voting → probability/confidence calibration → decision gates → persistence in `signal_accuracy` → later outcome evaluation and retraining. The separate generic `SignalService`/`/signals` workflow should not be confused with this dashboard path. The dashboard API builds a shared superset asynchronously and filters the result afterward; the UI asks for a minimum confidence of just 0.25.

## P0 — Fix correctness before tuning models

1. **Automatic training is arithmetically unreachable on its normal path (reproduced).** `services/auto_retrain_pipeline.py:143-152` takes **at most 20 symbols**, `:189-218` extracts **one feature/target pair per symbol**, and `:221-230` requires **at least 50 samples**. A synthetic test with 20 symbols and 100 historical observations *each* still collected 20 feature samples, skipped all models, and never called `train_for_market`. The “bootstrap” sliding-window trainer at `:264-425` is only reached if the first history query returns zero rows *after* the top-symbol query succeeded (`:182-184`); it is not the normal training branch. This applies to the `AutoRetrainPipeline` path, not proof that no other, separately trained artifacts exist. **Repair:** build time-indexed historical samples with a genuinely subsequent outcome, split by time and symbol, and test that a nonempty history actually reaches training.

2. **Its existing normal-path target leaks the answer if the sample gate is bypassed.** In `services/auto_retrain_pipeline.py:190-218`, features use the entire series through `closes[-1]`; the target is the price change from earlier closes *to that same* `closes[-1]`. This is retrospective momentum already present in the feature window, not an unseen future return. Increasing the symbol cap alone would enable training on a misleading supervised target. The separate bootstrap branch uses forward-looking window endpoints but is not normally entered. **Repair:** index every sample at time *t*, compute features from data at or before *t*, label only from prices after *t* at the matching prediction horizon, and validate strictly forward in time.

3. **Outcomes are assigned at the wrong horizon (reproduced).** The generator supports daily/2-day/3-day/weekly/monthly/quarterly horizons (`services/multi_market_signal_engine.py:349-353`), but `_evaluate_past_signals` selects *every* pending signal aged 5–30 **calendar** days without a timeframe predicate (`services/quant_signal_orchestrator.py:1819-1842`). It compares entry against the **latest** snapshot (`:1858-1910`), not a price at the correct horizon. The synthetic probe confirmed a six-day-old `monthly` signal is marked correct and recorded. Moreover, rows older than 30 days are excluded forever by this query if they were not evaluated earlier (e.g., an outage or backlog); the `LIMIT 100` can compound this. Thus apparently strong longer-horizon historical accuracy is not evidence of successful monthly/quarterly forecasts unless the stored labels are independently audited. **Repair:** store `due_at`, label only after the appropriate number of *market trading sessions*, get an as-of exit observation, retain overdue rows in the backlog, and record unknown/stale-feed outcomes separately from losses.

4. **Market accuracy can be a last-source-wins overwrite (reproduced).** `SignalAccuracyTracker.get_accuracy_by_market` groups by **market and source** (`services/signal_accuracy_tracker.py:193-211`), whereas `_get_accuracy_snapshot` assigns `snapshot[market] = item.accuracy_pct` for each returned row (`services/quant_signal_orchestrator.py:1948-1966`). This can depend on query ordering and disregard group sizes. In a synthetic probe, 100 outcomes at 20% and one at 100% yielded a displayed/thresholded **100%** stock snapshot, versus a weighted aggregate below 21%. `AutoRetrainPipeline.check_and_retrain` separately takes an *unweighted mean* of source accuracies (`services/auto_retrain_pipeline.py:87-101`). **Repair:** aggregate correct/total once per market, preserve a separate source-level breakdown, and base alerts/training triggers on a minimum sample count and recent, correctly matured cohorts.

5. **Checked-in API startup is broken.** `apps/api/router.py:223-226` contains unresolved merge-conflict markers; Python compilation and full backend test collection fail. The declared `requirements.txt` also conflicts over SQLAlchemy with `tehran-stocks==2.0.0`; merged Compose configuration cannot render an `api` service because it lacks image/build configuration. These are concrete local startup blockers, not evidence of what is deployed elsewhere. Clear them before claiming any live signal pipeline is healthy.

## P1 — Why apparent “ML + gates + feedback” may not deliver the intended protection

- **ML market coverage is narrower than rule-market coverage.** The seven rule generators include currency, commodity, options and IME (`services/multi_market_signal_engine.py:370-379`), but the ML-history loader maps only stock/gold/crypto (`services/quant_signal_orchestrator.py:924-968`); signals without five closes are skipped for this ML path (`:879-885`). With no loaded model, `MLSignalConnector.predict` falls back to heuristics where possible, or neutral (`services/ml_signal_connector.py:233-279`). Do not treat the “ML enabled” UI switch as proof of a trained forecast for every displayed signal; measure actual `models_used` per market.
- **Periodic repair is not reliably scheduled.** Outcome evaluation/retrain happens only after the generator has produced nonempty raw signals (`services/quant_signal_orchestrator.py:667-687,811-817`), skips its first process call and throttles subsequent calls to once per six hours (`:1614-1630`). `_last_scheduled_retrain` starts `None` and `_should_scheduled_retrain` refuses to run while it remains `None` (`:1594,1701-1710`); the only local assignment is inside the already-triggered periodic branch (`:1692`). This seven-day periodic route therefore does not bootstrap itself in this class. Separate manual/other training jobs may exist, but they do not make this particular loop periodic. The `/multi-market-signals/retrain` endpoint defaults `force=False` with trigger `manual`, while `check_and_retrain` only schedules work for `force=True` or an `accuracy_drop` trigger (`apps/api/endpoints/multi_market_signals.py:295-321`; `services/auto_retrain_pipeline.py:104-119`): an unforced manual request reports success without retraining.
- **Decision-gate inputs include proxies and a fail-open check.** When histories are absent, the data-quality gate invents a price-point count from voting coverage (`services/quant_signal_orchestrator.py:1207-1223`). Liquidity/fill probabilities are derived from absolute *price change*, not traded volume/order-book depth (`:1224-1228`); portfolio approval is unconditionally true because no portfolio validator is invoked (`:1230-1240`). Those calculations are not evidence of actual data freshness, liquidity or portfolio-safe execution, especially in markets without ML histories.
- **The dashboard can hide errors and “building” status.** The API may return `signals: []`, `building: true`, and `success: true` while a cold-start build runs (`apps/api/endpoints/multi_market_signals.py:214-227,282-286`). The main signals page checks the empty array but not `building` (`frontend/src/app/signals/page.tsx:43-78`), so “no signals found” also covers “not computed yet.” Other pathways in `services/signal_service.py:76-100` likewise convert certain failures into successful hold/empty responses; that service is a separate signal workflow, so this is not proof that the main dashboard used it. The job definitions in `jobs/definitions/signal_jobs.py:19,31` invoke two methods absent from `SignalService`; they would fail **if invoked**, but these definitions were not found wired into the main APScheduler registration.
- **Calibration and ranking are not an economic success criterion.** The UI requests a 0.25 confidence floor (`frontend/src/app/signals/page.tsx:36`); quality-gate inputs above are partly synthetic. The training report estimates improved post-retrain accuracy as `old_accuracy + 0.03` rather than measuring holdout performance (`services/auto_retrain_pipeline.py:250-255`; bootstrap similarly `:421-426`). Even true directional accuracy is distinct from after-cost expectancy, drawdown and execution feasibility.

## Historical evidence, with limits

Two checked-in August 2026 assessments report different historical snapshots: `docs/quant-signal-goal-assessment.md:75-107` gives **36.73%** accuracy on **3,695** evaluated signals and **−15.2%** paper-trading return; `docs/accuracy-investigation-2026-08.md:1-48` gives **38.48%** overall and roughly **25% daily** accuracy (3,117 daily outcomes). They disagree on the interpretation of the commodity breakdown: one explores possible directional/data issues; the other calls it a crash-regime effect. Neither is a fresh September 24 database measurement, nor can their monthly/quarterly numbers establish real horizon-specific skill given the evaluation code above. Treat regime explanations and financial performance as **historical, unverified here**, not conclusions drawn from the synthetic probes.

## Prioritized recovery plan

1. **Restore a runnable baseline:** resolve router conflict, dependency constraints and Compose service definition; run full backend CI before changing trading logic.
2. **Audit data and outcome chronology:** compare source timestamps versus signal creation, inspect pending rows older than 30 days, and re-label historical outcomes by market calendar and timeframe using reproducible as-of prices. Keep old and corrected metrics separate.
3. **Rebuild retraining:** use many point-in-time samples per symbol and forward targets; require leak-free walk-forward evaluation, minimum samples, persisted model lineage and measured post-retrain performance. Make periodic training an independent, observable scheduled workflow.
4. **Correct metrics:** aggregate `correct / total` per market and horizon, show sample sizes and baseline; monitor calibration error, after-cost paper returns, maximum drawdown and fraction of predictions backed by actual fitted models.
5. **Harden delivery:** make missing history, stale feeds and unvalidated liquidity/portfolio gates explicit degraded states; distinguish cache-building/failed/empty on the UI; only market a candidate as actionable after calibrated expectancy and execution checks.
